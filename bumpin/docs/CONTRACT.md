# BumpIn Contract

Shared agreement between Backend A, Backend B and the frontend team. Edit this file in the same commit as any change to it.

## 1. Fake world

- Festival: Riverside, Friday 11 to Sunday 13 December 2026.
- Demo "today" (`festival.sim_today`): 2026-11-30, 11 days out. Anything dated within 14 days of the festival start counts as "inside the two-week window".
- Stages: River Stage (main), Lawn Stage (open-air), Dome Stage (small). One shared equipment pool (`stage_id` null) used by any stage.
- Scale: 60 artists and 40 vendors in the database. About 6 artists and 8 vendors are hand-crafted with real PDFs and emails. The rest are generated by a script with valid, mostly clean records. Show counts on the overview.

## 2. Data model (SQLite)

Primary keys are integer `id`. Timestamps are ISO 8601 strings. JSON columns hold JSON text.

- `festival(id, name, start_date, end_date, sim_today)`
- `stages(id, name, location)`
- `inventory_items(id, stage_id NULL, canonical_name, category, quantity_total, aliases_json)`
- `artists(id, name, manager_name, manager_email, stage_id, set_start, set_end, status, hospitality_cap NULL)`
- `vendors(id, name, type, contact_name, contact_email, uses_gas, site_zone, load_in_start, load_in_end, status)`  (`type`: food, beverage, merch, other; `status`: in_progress, completed, rejected; `load_in_*` are ISO timestamps on the Friday bump-in)
- `documents(id, owner_type, owner_id, kind, filename, path, extracted_text, expiry_date NULL, issuer NULL, received_at, email_id NULL)`  (`owner_type`: artist or vendor; `kind`: rider, permit, food_safety, insurance, gas, other)
- `emails(id, direction, from_addr, to_addr, subject, body, thread_id, received_at, classification NULL, confidence NULL, is_major_change, ticket_id NULL)`  (`direction`: in or out)
- `tickets(id, type, owner_type, owner_id, status, severity, summary, proposed_actions_json NULL, decided_by NULL, decided_at NULL, created_at, updated_at)`
- `findings(id, ticket_id, kind, severity, message, suggestion, doc_id NULL, quote NULL, page NULL, bbox_json NULL, status)`
- `rider_items(id, artist_id, doc_id, raw_text, quote, page, category, inventory_item_id NULL, quantity, unit_cost NULL, match_confidence)`  (`category`: technical or hospitality)
- `allocations(id, artist_id, inventory_item_id, quantity, start_ts, end_ts, status)`  (`status`: reserved or released)
- `outbox(id, ticket_id, to_addr, subject, body, context_used_json, status, created_by, approved_by NULL, sent_at NULL, mode)`  (`status`: draft, sent, failed)
- `audit_log(id, ticket_id NULL, actor, action, detail, at)`
- `notifications(id, for_user, ticket_id, text, created_at, seen)`

## 3. States and vocabulary

- Ticket `type`: `rider_needs`, `vendor_eligibility`, `help`.
- Ticket `status`: `open`, `needs_review`, `in_progress`, `approved`, `rejected`, `resolved`.
- Finding `kind`: `shortage`, `double_booking`, `over_budget`, `expired_cert`, `missing_doc`, `low_confidence`, `schedule_change`.
- Finding `severity`: `conflict` (red, only these are red), `warning`, `info`.
- Finding `status`: `open`, `ignored`, `resolved`.
- Actions: per finding, **Ignore** or **Resolve**. Per ticket, **Approve** or **Reject** (with reason). Per help-ticket action, **Approve** or **Edit**.
- Roles in text: the **user** is Ravi or Jess; the **client** is the artist or vendor.

## 4. Pipeline

1. `POST /api/inbox/receive` stores the email and its attachments.
2. Extract text: PDF text layer with PyMuPDF; images via a vision LLM fallback.
3. `classify(text)` returns a label and confidence (section 5).
4. Route: `rider` goes to artists, `vendor_doc` goes to vendors, `help_or_change` creates a `help` ticket, `unsure` creates a `needs_review` ticket.
5. Extract structured items, each with an exact source quote.
6. Run the checks in plain code. Create findings, with highlight boxes where possible.
7. AI writes a short explanation and a suggestion per finding, using the rule files.
8. A human acts. The reply is drafted into the outbox, edited if needed and sent by a human.
9. Everything is written to `audit_log`. The other user is notified (section 11).

## 5. Classifier (Jev-style)

```python
class Classification(BaseModel):
    label: Literal["rider", "vendor_doc", "help_or_change", "unsure"]
    confidence: float          # 0 to 1
    reason: str
    sender_role: Literal["artist", "vendor", "unknown"]
    entity_hint: str | None    # artist or vendor name if found
    is_major_change: bool      # set time moved, cancellation, stage change, equipment quantity change, vendor withdrawal
```

Method: two independent LLM calls with enum-constrained JSON output. If the labels differ, `confidence = min(confidence, 0.5)`; otherwise use the mean. Do not describe this as calibrated.

Routing policy:

- confidence >= 0.90: file automatically, visible in the log.
- 0.60 to 0.90: `needs_review`, shown in Ravi's batch.
- below 0.60: `needs_review`, shown at the top.
- Any finding about a critical field (insurance, food safety, gas, permit, expiry): always `needs_review`, regardless of confidence.
- `is_major_change` and `festival.sim_today` within 14 days of `start_date`: create a notification for Ravi immediately.

### Ticket handlers and endpoint ownership

The generic ticket endpoints live in `shared/tickets.py` (Backend B). They dispatch by `ticket.type` through a handler registry in `shared/registry.py` (Backend B):

```python
class TicketHandler(Protocol):
    def approve(self, ticket_id: int, actor: str, payload: dict | None) -> None
    def reject(self, ticket_id: int, actor: str, reason: str) -> None
    def resolve_finding(self, ticket_id: int, finding_id: int, actor: str) -> None
    def ignore_finding(self, ticket_id: int, finding_id: int, actor: str) -> None
    def approve_action(self, ticket_id: int, index: int, actor: str) -> None   # help tickets
    def edit_action(self, ticket_id: int, index: int, actor: str, edits: dict) -> None

register_handler(ticket_type: str, handler: TicketHandler) -> None
```

- Backend A registers `rider_needs` and `help` (artist changes and the ripple). Backend B registers `vendor_eligibility`.
- Every handler method calls `decide()` first, so first-approval-wins and the audit log always apply.
- The inbox pipeline (Backend B) creates tickets through these functions, chosen by label and sender role: `artists.create_rider_ticket(email_id, classification)`, `artists.create_help_ticket(email_id, classification)`, `vendors.create_vendor_ticket(email_id, classification)`, `vendors.create_vendor_change_ticket(email_id, classification)`. Each returns a ticket id.
- `main.py` (Backend A) includes `artists.routes.router` plus every router in `shared/router_registry.ROUTERS`. Backend A creates `router_registry.py` containing `ROUTERS = []` in the skeleton commit. Backend B appends to it afterward. This is the one allowed edit across ownership lines.
- Endpoint owners. Backend A: `/overview`, `/artists`, `/inventory`, `/runsheet`, `/export/runsheet.xlsx`, `/documents/...`, `/demo/reset`. Backend B: `/tickets...`, `/inbox/receive`, `/outbox...`, `/vendors`, `/phone/cards`, `/notifications...`.

## 7. API (JSON, prefix `/api`)

Header `X-User: ravi | jess` identifies the actor.

- `GET /overview`: counts and readiness (suppliers, documents, needing attention, expiring soon, open conflicts).
- `GET /tickets?type=&status=` and `GET /tickets/{id}`: the detail includes findings, documents, proposed actions, the draft email and `context_used`.
- `POST /tickets/{id}/findings/{fid}/ignore` and `.../resolve`.
- `POST /tickets/{id}/approve` and `POST /tickets/{id}/reject` with `{reason}`. Returns 409 with `{decided_by, decided_at}` if already decided.
- `POST /tickets/{id}/actions/{index}/approve` and `.../edit` (help tickets).
- `GET /documents/{id}/file` and `GET /documents/{id}/highlights` (list of `{page, rect, finding_id, severity}`).
- `POST /inbox/receive` with `{from, subject, body, attachments[]}` runs the pipeline.
- `GET /outbox`, `PATCH /outbox/{id}`, `POST /outbox/{id}/send`.
- `GET /inventory`, `GET /artists`, `GET /vendors`, `GET /runsheet`, `GET /export/runsheet.xlsx`.
- `GET /phone/cards?user=ravi`: action cards (needs_review items, major changes, pending approvals), most urgent first.
- `GET /notifications?user=` and `POST /notifications/{id}/seen`.
- `POST /demo/reset`: reload seed data and `sim_today`.

## 8. Rule files (`data/rules/`)

- `vendor_eligibility.yaml`: required document kinds per vendor type, whether gas applies, minimum validity (must cover the festival end date), minimum insurance cover. Owner: Backend B.
- `hospitality.yaml`: caps and unit costs for dressing rooms, beverages and comfort items. Owner: Backend A.
- `actions.yaml`: recommended steps per finding kind, used as the "Action" text. Shared, each owner adds their kinds.
- `email_policy.md`: tone, sign-off, what we never promise, how to phrase rejections. Loaded into every drafting prompt and listed in `context_used`. Owner: Backend B.

## 9. Email

- `EMAIL_MODE=mock`: sending writes the outbox row as `sent` and shows the preview. No network.
- `EMAIL_MODE=demo`: also delivers to `DEMO_RECIPIENT` only, never to the artist or vendor address.
- Every drafted email stores `context_used` (file or entity names the AI read) and shows it in the UI.

## 10. Highlights

For digital PDFs: the LLM returns the exact quote for each requirement. Find it in the text layer with PyMuPDF `page.search_for(quote)` and store the rectangles in `findings.bbox_json`. If the quote cannot be located, store the finding without a box and show the quote as text. Images and handwriting get no highlight.

## 11. Concurrency and notifications

- Decisions go through `decide()`. The first approval or rejection wins and writes `decided_by` and `decided_at`.
- A later attempt returns 409 with who decided and when.
- When Jess decides, Ravi gets a notification with what changed and who was told (and the reverse). Stretch goal: a 60 second hold before outside emails send, with a stop button.

## 12. Seed data ownership

- Backend A: festival, stages, inventory, artists, rider PDFs (generated with reportlab or fpdf2), the bulk generator for 60 artists, hospitality rules.
- Backend B: vendors, certificate and permit PDFs, the vendor and help emails (items 4, 5, 6, 7 and 8 in the planted list), the bulk vendor generator for 40 vendors, eligibility rules and email policy.
- Run `POST /demo/reset` to rebuild everything from seed files.
